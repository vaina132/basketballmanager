# Technical architecture

Design baseline: 5 November 2026. Implementation notes updated: 14 November 2026. The opening sections describe the target; the implementation sections distinguish working behavior from remaining systems.

## 1. Runtime choice

Use TypeScript for a browser-independent domain/simulation core and a React management interface. Vite produces static assets compatible with the user's intended hosting. The application initially needs neither accounts nor a game server. Pin compatible package versions and a lockfile at setup rather than treating a documentation example as a permanent latest version.

[Vite's guide](https://vite.dev/guide/) documents its development server and static production build. [React's installation guidance](https://react.dev/learn/creating-a-react-app) discusses both framework and build-tool approaches. The client-only choice here is a project decision based on the confirmed local single-player scope.

Use a renderer adapter for the diagonal court. The first fixture can use SVG or Canvas 2D for a minimal view; the target animated presentation can use [PixiJS](https://pixijs.com/8.x/guides/getting-started/intro), a 2D scene renderer supporting WebGL and WebGPU. Rendering never determines scores or consumes gameplay random numbers. Keep a readable scoreboard and event feed when graphics are unavailable.

An initial increment may colocate small modules, but dependencies point inward: engine code must not import React, browser storage, or animation APIs.

## 3. Authoritative state

Entities use stable IDs. Store identities once and reference them across domestic, European, youth, scouting, and finance contexts. A player transfer changes membership and contracts; it does not create a new player.

Core entities: World, Season, Competition, CompetitionEntry, Ruleset, Club, Team, Player, StaffMember, Contract, Registration, Fixture, MatchState, TrainingPlan, Injury, ScoutingAssignment, Report, Promise, InboxEvent, Facility, CommercialAgreement, LedgerEntry and Career.

Each record declares what owns it. The health subsystem owns recovery; matches produce exposure and incidents. Finance owns obligations; transfer completion requests validated accounting transactions. Scouting stores knowledge separately from player truth. UI selectors expose the information appropriate to the managed club.

Local single-player storage cannot securely hide attributes from a determined file inspector. Scouting secrecy is a gameplay rule, not an anti-cheat guarantee.

## 4. Commands and events

Commands contain an ID, expected state revision, payload, and requested boundary. Validate against authoritative state before accepting. Repeating an accepted command ID returns its previous result rather than applying it twice.

Examples: AdvanceToNextEvent, SetTeamInstructions, QueueSubstitution, RequestTimeout, SubmitOffer, AcceptContract, SetTrainingPlan, AssignScout, SetTicketPrice, ProposeFacilityProject, SetDelegationPolicy.

Events record facts already resolved, with stable IDs and world/match timestamps. Examples: ShotResolved, MatchCompleted, ContractSigned, PayrollPosted, InjuryDiagnosed, ScoutReportDelivered, PromotionConfirmed. Store essential reasons so the interface can explain changes without reverse-engineering them later.

Use snapshots plus a bounded event journal. Keeping every animation frame and every historical match action forever is unnecessary. Preserve career history, box scores, important decisions, and selected replays under an explicit retention policy.

## 5. Deterministic simulation

Use explicit seeded random generators with versioned algorithms and separated domains. Save each generator's state. Derive fixture-specific seeds from stable fixture IDs; scheduling work on a different worker must not change the match.

The engine uses integer simulation time and documented rounding. No Date.now(), Math.random(), requestAnimationFrame timing, browser locale, or unordered iteration may influence sporting outcomes. Equal initial state plus equal effective commands must produce equal outcomes across playback modes.

Run a match by stepping authoritative actions or by calling the same step function until a stop condition. Quarter skipping is a stop condition, not a different score generator. Mid-action saves retain unresolved penalties, free throws, commands, and random state.

Separate reproducibility from historical compatibility. A new engine version may intentionally change outcomes; an old career must stay pinned to a supported version or undergo an explicit migration with an explanation. Never silently promise identical replay after changing the probability model.

## 6. Worker and world scheduler

Long simulations belong in a Web Worker; [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) documents background execution and message-based communication. UI animation uses separate timing and interpolates already resolved events.

Worker messages include operation ID, command sequence, revision, progress, result, and structured errors. Allow cancellation only at a committed boundary. Terminating a worker must not leave a half-posted result or salary payment.

Define stable world phases per date: scheduled administrative events, health/training, transfer/AI decisions, fixture kickoffs ordered by simulation time, match completion, post-match reactions, and closing bookkeeping. Resolve cross-club negotiations in a stable order or explicit simultaneous batch. Parallel execution may compute independent matches, but authoritative commits remain deterministic.

Fixtures share the same club, player, contract, eligibility and injury records. A world barrier prevents later decisions from observing some same-time results but not others merely because one worker finished earlier.

## 7. Persistence and recovery

Use IndexedDB for saves; it supports indexed structured records and transactions. Storage is local to an origin and subject to browser quota/eviction, so import/export and clear save status are core features. See [MDN's IndexedDB reference](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API).

Save envelope: formatVersion, schemaVersion, engineVersion, rulesetVersions, dataPackId/version, calibrationVersion, careerId, revision, createdAt, simulatedDate, RNG states, payload checksum, and payload. Wall-clock metadata is permitted in the envelope but not sporting calculations.

Write a new revision transactionally, verify it, then move the active-save pointer. Retain at least a previous known-good checkpoint where quota allows. Never display "saved" before the storage operation succeeds. Handle quota denial with a recoverable state and export action, preserving the in-memory game.

Import treats files as untrusted data: size limits, JSON/schema validation, finite/ranged numbers, entity references, allowed versions and identifiers. No executable script, HTML insertion, arbitrary asset fetch, or prototype mutation from a save. Validate entirely before replacing the active world. A checksum detects accidental corruption, not malicious authenticity.

Save size (24 November 2026): the game writes the compact-3 layout (`compact-json.ts`, packed records in `save-packing.ts`, completed seasons sealed at rollover in `sealed-history.ts`) and stores that text compressed (`compact-3-deflate`: raw DEFLATE in base64 inside a readable envelope; `save-compression.ts`, dependency-free coder in `deflate.ts`). Compression is lossless and applies to every save the game writes, older careers included; the inner text must be a compact-3 save of the same format and passes the same checks. The 32 MB limit applies to the stored text; the compact text inside may reach 128 MB. Sealed seasons also keep only the scouting reports later readings use (observed reports of players still playing; all of the managed club's, the latest three per player elsewhere). Ten-season careers store about 2.6-4 MB instead of 11-16 MB and grow by about 0.25-0.5 MB a season.

Multi-tab play uses one writer lease with conflict detection; a second tab can view or take over explicitly. Reload, canceled simulation and season rollover must recover from a completed revision rather than repeat an event.

## 8. Data and assets

Import tools run separately from the production gameplay client. Ship a versioned pack; do not have each browser scrape league sites during play. Preserve original source values and derivation metadata; normalize units and identities into the domain schema.

Store portrait and court appearance references together. Load images lazily and provide consistent illustrated fallbacks. Future full portraits and sprite artwork can replace development primitives without changing player identity or skills.

Third-party data and image permissions are independent of this repository's Apache software license. Maintain a separate data/asset manifest and distribution status.

**Career worlds (format 39).** Game logic never reads the built-in league's data modules directly; it asks for the career's world with `worldOf(context)` (`src/world/career-world.ts`), which returns `SeasonState.world` or, for careers without one, `DEVELOPMENT_WORLD` (`src/data/development-world.ts`). Catalog, lifecycle, facilities and finance contexts include the optional `world`/`dataPackId` fields (`WorldContext`); contexts built by hand inside validators pass `world` explicitly. Rivalry, president and sponsor helpers take the world as an argument (`rivalryFor`, `governingDerby`, `verdictBudgets`, `sponsorAppeal`, `buildSponsorshipOffers`). `createSeason({ world })` starts a career in a world after `validateWorld`; only non-built-in worlds are stored (`storedWorld`). `tests/career-world.test.ts` plays a full career in a renamed copy of the built-in league, so any remaining direct read of built-in data fails; tests of non-built-in worlds switch on `requireWorldContexts(true)`, which makes `worldOf` throw for a context that carries neither `world` nor `dataPackId`.

**Season length (2.8b).** A world's season is a double round robin of `worldRounds(world) = 2 x (clubs - 1)` matchdays; rules ask `seasonRounds(context)` instead of assuming ten. Matchday numbers that are stored in saves or counted across seasons use `roundOrdinal(season, round, rounds)` = `(season - 1) x rounds + round` (the built-in league's stored values are unchanged); numbers used only to compare calendar positions use `roundKey(season, round)` = `season x 100 + round`. Range checks that do not know the career accept up to `MAX_SEASON_ROUNDS` (78). Staff candidates come from shared directories (`src/data/staff-directory.ts`): lookups by id use the whole directory, candidate lists use the league's market (`staffMarket`), sized like the built-in league per club; sponsors work the same way (`SPONSOR_DIRECTORY`, `sponsorMarket`).

**Compact saves (format 40, 2.8d).** `compactJson`/`expandJson` (`src/storage/compact-json.ts`) turn the state into a shape table (each ordered key list once), a string table (each text of 10+ characters used more than once) and an array tree; `serializeSeasonCompact` writes `{ format, formatVersion: 40, engineVersion, encoding: 'compact-1', strings, shapes, state }`. `parseSeason` expands compact files before the usual checks, so validation is unchanged. Youth status checks use a per-player index cached per `SeasonYouthCompetition` object; `getContractedClubsForRound` caches frozen results per employment, academy and world.

**Current compact saves (formats 41–43).** `compactJson2` also shares repeated subtrees in a `nodes` table (`compact-2`), with bounded preflight expansion and independent decoded objects. Every checkpoint write and portable import/export is fully validated. Versioned SHA-256 fingerprints stored separately in IndexedDB permit fast local reads of unchanged, previously validated text; missing/stale fingerprints or unavailable Web Crypto use full validation. The fingerprint salt includes both schema and checks versions; it is not an authentication mechanism for imported summaries.

**Academy history outcomes (format 42, step 3.2c).** `world/academy-history.ts` changes older rival `AcademyWeek.players` reports to the explicit union member `{ detail: 'outcome', clubId, focus, pointsAfter }`. Full reports remain required for the current season, the club managed in the report's season (`managedClubFor(..., false)`), the global latest week and each club's latest nonempty week. Older eligible full reports remain valid. Rollover summarizes immutably; legacy migration first validates the original detailed state, then summarizes and validates again. Every interval, prospect membership, coach assignment and exact accumulated point total remains. Strict replay regenerates each full report and compares its projection with the outcome, keeping independently calculated points. Validators never accept a summary's totals just because a hash matches. UI report readers narrow the union before reading gains/availability. This reduces redundant historical objects, not the number of retained weeks; youth fixtures, financial journals, senior statistics and prefix references remain unchanged.

**Youth fixture outcomes (format 43, step 3.2d).** `world/youth-history.ts` replaces eligible old rival `YouthFixtureFull` records with `YouthFixtureOutcome`: the same fixture identity/calendar, null `home`/`away`/`startingConditions`, explicit `detail: 'outcome'`, ordered `playerIds: { home, away }`, and the complete nonnull result. A once-built retention context protects current seasons, the historically managed club and either club's latest completed fixture. Full old records remain valid. `getYouthFixtureTeams(fixture, state)` reconstructs an outcome from `academyAtBoundary` at the actual fixture season/round through the shared live team builder, checking ordered IDs and preserving original attributes and shirt-number collisions. It does not use current senior rosters, future academy points or a possession replay. `youthCompetitionAtBoundary` returns canonical unsettled shapes when hiding later results, removing outcome-only fields.

Strict youth replay independently prepares all original teams and starting conditions, compares full or projected inputs as appropriate, and retains existing result conservation, participation, injury and default checks. Stats/injuries remain available to health, practice, promotions, standings, performance and historical MVP selectors. Migration fully validates the source: formats below 42 receive academy reduction, format 42 keeps its existing academy representation, then older-than-43 states receive youth reduction and validate again. Current-format loads preserve optional full records. Rollover applies academy then youth reduction immutably. Neither fixture counts nor financial journal prefixes are pruned; finance's 20,000-row limit and incremental strict-validation work remain open. Independent original-runtime migration/continuation comparisons, 117 focused tests, the build, 13 browser storage checks and the full 2,302-test/153-file regression passed; [3.2d measurements](multi-league-world.md#step-32d-historical-youth-fixture-outcomes-14-november-2026) distinguish structural savings from heap use. The paired old/current timing diagnostic also passed state/hash checks; median strict-read and validated-write timings were effectively unchanged within run variation.

**Real-club worlds (2.8c).** `worldFromPack(pack, competitionId)` (`src/world/real-world.ts`) turns one domestic league of a parsed data pack into a validated `CareerWorld`, filling what the pack lacks by `REAL_WORLD_RULES`. `CareerStart` loads the pack (shared `realPack` state in `App`), offers `careerCompetitions(pack)`, and `App.startSeason` passes the world to `createSeason`.

**Logical financial history (step 3.2e, format 43 unchanged).** `world/finance-ledger.ts` exposes `financeLedgerCount`, absolute `financeLedgerEntry`, ordered half-open `financeLedgerEntries`, fresh `financeLedgerSlice`, `financeAtLedgerBoundary` and `appendFinanceLedgerEntry`. Bounds are safe integers within the logical ledger; negative lookup never means the final row. Append keeps sequential `finance-N` IDs and the existing club/kind/source duplicate guard. `SeasonFinance.ledger` is still the original complete array. No transaction, ID, absolute anchor or save representation is removed by this prerequisite; schema 43, checks version 3 and the 20,000-entry finance limit stay unchanged.

`world/finance-ledger-index.ts` provides exact club balance/net and per-agreement payroll totals at those transaction positions. `scopedCalculation` enables reuse only within one synchronous `withCalculationCache` scope. Prefix arrays keep ordinary array isolation while a scope-local origin identifies their original ledger and exclusive end. Nested prefixes retain absolute positions; nonzero slices get independent accounting. Index keys include replay-array length. Subsequent validations rebuild derived facts after mutations, and returned balances/payroll totals are fresh values. An unscoped payroll reader is a local snapshot for one operation. The index aggregates all payroll items, including multiple items within a charge, and preserves empty payroll boundary rows. Strict validation still checks original order, sources, membership, balances and commitments; no index is a validation certificate.

**Lossless financial archives (format 44, step 3.2f).** `SeasonFinance.archives` holds optional, ordered `finance-archive-1` blocks: completed season, absolute first index and rows `[clubId, round, kind, amount, sourceId, details]`. Only the block's common season, sequential `finance-N` identities and null ticket/coach/payroll defaults are implicit. All non-null and optional payloads, including empty payroll markers, remain. `ledger` is the active tail. `world/finance-archives.ts` archives complete seasons at rollover after the offseason; the logical adapter streams rows and looks up absolute positions without keeping a permanent expanded copy. Prefix snapshots remove archive metadata to prevent double-counting. Derived index ownership distinguishes different archived histories sharing an active array.

Frequent unscoped balance, payroll and ticket-capacity reads use `financeLedgerAmounts`, `financeLedgerPayrollCharges` and `financeLedgerTicket`. These iterate primitive amounts or borrow original payloads directly from archive tuples and the live tail, preserving order, empty payroll charges and missing-capacity behavior. They neither cache totals nor certify evidence. Callers must keep borrowed payloads immutable. This avoids expanding every archived transaction repeatedly for each club or ticket-price candidate; scoped historical validation still uses the full row/index path.

`storage/finance-archive-validation.ts` checks block models, contiguous offsets, ordered completed seasons, tuple/payload shape and resource bounds before making one temporary full view. Every existing accounting, mandatory-event, chronology, adjacency and historical-command check then runs against that view; it is discarded afterward. Formats 1?43 validate as written before migration and again afterward. Current-format files are not silently repaired. The schema changes the local seal salt; checks version 3 and `compact-2` remain. Portable imports/exports and checkpoint writes stay strict.

Format 44 allows at most **20,000 active-tail rows**, **20,000 rows per archived season**, **100 archive blocks** and **200,000 logical transactions**. Original formats retain their 20,000-total constraint before migration. The existing 32 MiB file guard remains; the 16-million-value, 200,000-element collection and depth-40 guards also apply to decoded/reconstructed data. Append checks the season being written, allowing strict replay's temporary multi-season prefix to exceed 20,000; it still enforces the logical total and prevents writes into archived years. These are explicit finite safety limits, not an unlimited-career or multi-league capacity guarantee. Other journals have their own limits. Financial ownership continues to use `managedClubAtLedger`, including same-season job moves.

**Career calculation batches (step 3.2g, format 44 unchanged).** Historical registration reconstruction builds each calendar boundary's player lookup and contracts grouped by club once per reconstruction. Opening membership still follows catalog order; later arrivals follow contract order, preserving jersey collisions, departures/returns and graduate availability. These local lookups do not add a persistent cache.

AI candidate filtering for coaches, scouts, fitness coaches, physios, assistants and youth coaches runs inside a short `withCalculationCache` scope. Only quotes against unchanged state share financial indexes. The scope is released before sorting/selection and before the authoritative hire command, which checks affordability again. A later club or appointment receives a fresh scope. Never hold these derived facts across state mutation or use them to accept imported evidence.

**Registration replay boundaries (step 3.2h, format 44 unchanged).** `registrationChangeRounds` shares the existing sorted, distinct contract/transfer effective-start rounds with storage. `rostersForEmploymentYear` reconstructs the opening squad and each candidate change, comparing complete player records before adding a snapshot. **Relationship evidence windows (step 3.2i, format 44 unchanged).** Each `clubHistory` calculation groups that club's role/talk journal by player without changing event order. ## 9. Performance budgets and evidence

Initial measurement goals, not current guarantees: responsive controls during a simulated day; a representative watched match near display refresh rate; no growing memory allocation per rendered frame; resumable season work with visible progress; bounded historical replay storage.

Measure the approved ten domestic divisions and three European competitions before promising season-simulation times. Record hardware, browser, dataset size, fixture count, median and slow-tail duration. Benchmark both simulated games and off-court AI, which may dominate a large world.

Optimize based on profiles: batch snapshots, virtualize long lists, cache derived read models with revisions, compact completed match events, and limit simultaneous workers. Preserve deterministic ordering throughout.

## 10. Verification strategy

Use scenario and property/invariant tests for engine legality, accounting, eligibility, replay, import/export and rollover. Statistical harnesses examine aggregate behavior with confidence intervals and pinned seeds. They complement rather than replace rule tests.

UI checks cover actual journeys: selecting a lineup, watching/skipping, making a legal substitution, recovering a save, scouting a player, negotiating and registering a signing. Avoid tests that merely duplicate implementation formulas or snapshot large unreviewed trees.

Validate build and types on each implementation milestone. Browser QA should cover both a desktop and tablet layout when tooling is available; record limitations instead of claiming visual checks that were not performed.


## 11. Current season implementation

The development league uses `SeasonState` (`schemaVersion` equal to `SEASON_SCHEMA_VERSION`, currently 43, `engineVersion: possession-3`, `dataPackId: development-league-1`); the later sections describe the systems each format added. It owns the clubs, plans, conditions, career injury mode and committed injury history, training, coaching contracts, club facilities, finance, player payroll, employment terms, per-club scouting knowledge, negotiation history, dated offseason and in-season recruitment journals, season number, prior season archives, deterministic current schedule, compact results and one active match. App holds a discriminated exhibition/season session; in season mode its match view is a projection of `season.activeMatch`, not a second authoritative match copy.

Each fixture has an independent seed derived from the career seed and fixture ID. Season 1 retains its original IDs; later fixtures include the season number, providing distinct yearly streams. Round completion computes the other two matches in a module Web Worker, then returns one new immutable season snapshot. The same worker handles dated recruitment advances and rollover after the final round is committed. A request identifier rejects stale replies. Cancellation terminates the worker and retains the previous completed match or season. Loading another session invalidates the worker; asynchronous reads also have a generation guard so they cannot overwrite later commands.

The fictional calendar advances seven days after a committed round. With training disabled, condition recovers by a provisional three points per day for every club, once; enabled training applies the workload and availability rules in section 12. Recovery episodes use a separate deterministic hash of career seed, fixture, player and injury kind, without consuming sporting RNG. The first recovery model uses 7-28 calendar days for ankle incidents and 7-21 for muscle incidents; these are uncalibrated game parameters. A player becomes eligible on returnOn. Pausing, reloading and opening a report do not advance recovery. After all ten rounds are finalized, rollover archives that season once and prepares the following year's first Saturday in September. The exact offseason interval determines recovery; history is retained even after clearance. The four-digit save calendar supports season numbers 1-7974, with rollover beyond year 9999 rejected and no recruitment window beyond the final supported year. Clubs remain stable; when employment is enabled, roster changes, lineup repair and training-plan membership are applied atomically at rollover. Earned development persists by player ID.

Season files use the distinct `basketball-manager-season` envelope. This paragraph records the format-13 increment, which then had an 8 MB limit; the current format is `SEASON_SCHEMA_VERSION` (43) with the 32 MiB `MAX_SEASON_SAVE_BYTES` limit, and each later section records its own migration. Versions 1–12 are checked against their original constraints, then migrated in memory while preserving their active match exactly and adding a disabled offseason calendar. Formats 1–11 also gain disabled negotiations; format 12 preserves its existing response journal. Formats 1–10 gain disabled scouting; format 11 preserves it. Formats 1–9 also gain disabled employment; later versions preserve their employment state. Versions 1 and 2 gain season 1 with no archived seasons; later formats retain their existing career history. Formats 1–3 gain disabled training with zero development; format 4 retains its training plans, points and outcomes. Formats 1–4 gain disabled coaching with no contracts, and retained training reports gain zero coaching attribution. Formats 1–5 gain disabled finances with default plans and an empty ledger. Existing coaching and training state is retained. Formats 1–6 gain disabled player payroll; format 6 retains its financial history. Formats 1–7 gain a null manager profile; later formats retain it. Version 1 also receives injury mode off with empty injury history and result injury maps. Formats 1–8 reconstruct known roster membership but cannot recover discarded archive box scores; format 9 retains its snapshots and archived player records. No stored file is rewritten until a save. Full events are retained only for the active game. Compact player statistics are retained for current fixtures and new archives; old imported archives explicitly lack those statistics. Each prior season retains its canonical schedule, earned and official scores, winner, outcome, periods and injury map; standings are derived from those results. Archives are contiguous and never silently truncated. Validation checks fixture order/dates, historical membership, result arithmetic, the condition-recovery boundary and the active match. It rebuilds career health history from archived and current fixture injury maps and rejects altered dates, diagnoses, overlaps, missing carried absences or exposure by unavailable players. Modern scheduled matches may contain optional preExistingInjuries metadata; those players have injury entries at zero elapsed time, zero match exposure and no fabricated new injury events. The UI projects current uncommitted incidents from the active match; only atomic matchday completion appends them to world history.

IndexedDB uses `basketball-manager-seasons`, separately from the exhibition database. IndexedDB version 2 retains the compatible current string and adds a revision counter and checkpoint store. Each save compares the caller's expected revision within a strict read/write transaction, writes the current snapshot and metadata, and prunes to five checkpoints atomically. The first new write preserves a previous single-slot save as revision 0. A tab remembers its revision; browsing history does not refresh write authority. A stale write fails without changes, and an explicit latest/older checkpoint load accepts the observed revision for a future save. This is optimistic conflict detection, not an exclusive writer lease.

New games, completed matchdays, recruitment-calendar advances, rollover and employment/scouting decisions create automatic checkpoints; manual saves can capture live matches. Contract and scouting activation, accepted offers, responsibility changes, observation assignments/cancellations and shortlist edits use the existing save/revision path. Restoration validates the selected snapshot and changes only the in-memory session until the next save. A damaged current payload opens recovery history; invalid entries are visible but cannot be restored. Failed writes retain prior checkpoints and keep the live game available for retry/export. Checkpoint timestamps describe device time and never enter sporting state or RNG. The five records share one local season slot, so separate careers still need exported files; automatic saving after every match action, named career slots and exclusive writer leases remain future work. Extremely long careers can still reach the 32 MiB limit; export/save fails explicitly rather than dropping history.

Strict validation for saving, loading, checkpoint restore, import and export runs in a reusable module worker (`src/storage/season-codec.worker.ts`, created on first use) so a long career never freezes the interface; if workers are unavailable or fail, the same codec runs on the main thread. The main menu validates only the current save and reuses that result for Continue at the same revision; Save history validates checkpoints when opened, once per identical text. Validation time still grows faster than career length (about 7 seconds per save for a 21-season career on the development machine); the academy and relationship replays dominate.


## 12. Initial training model

`SeasonTraining` owns the model identifier, activation season/round, every club's plan, per-player integer practice points and the latest weekly report. The stable development catalog owns base identities and ratings; `season.clubs` holds the current registered squads and `developClub` projects integer skill ratings when preparing a fixture. All sixty players retain practice points and condition, including unattached players. Weekly processing trains registered squads only. Live and finished match snapshots retain the ratings they started with. Changing a plan or enabling training never rebuilds that match or draws from sporting RNG.

After all three results are committed, the calendar interval processes each of seven days in stable player order. Health eligibility controls participation; workload affects condition and practice points through the same function for human and AI clubs. Cumulative points are bounded to 200 per skill, reduced where the authored rating is already near 20. Every 100 points grants one rating point. Balanced plans divide a fixed practice budget, rotating any remainder by matchday. Condition below 70 halves that day's practice budget. These parameters are explicit provisional models, not calibrated age/potential curves.

`lastWeek` retains the applied plans, dates, eligible days, condition inputs/outputs and gains. Save validation checks those inputs against the preceding committed fixture statistics, reconstructs prior points by subtracting recorded gains, and replays the exact interval with the committed health history. Current plan edits are independent of that report. Activation before the first processed interval and round 1 after rollover have no report; the former retains legacy recovery conditions and the latter retains offseason recovery. Final round 10 has no following training week; conditions initially match the final box score, then recover by elapsed days when the dated offseason calendar advances. The final match snapshot stays fixed. Rollover clears the report but retains points, plans and activation. Older interval reports are not archived, so cumulative development is bounded owned state rather than a fully replayable training ledger.

## 13. Derived season performance

`world/performance.ts` derives player totals and newest-first game logs from committed selected-season `FixtureResult` records and their referenced registration snapshots. It does not read the active match, modify the world, consume random numbers or add persisted data. The same projection drives squad statistics and league leaders. Imported older results work after their existing migration. The new current season starts with empty performance totals; retained archived box scores remain selectable. Imported old archives with null statistics expose an unavailable state rather than fabricated zero rows.

An appearance requires court time or a nonzero personal statistic; condition alone does not count. Formats 1-30 validate as written and migrate with negotiations disabled; earlier systems keep their stored state, and genuine format-30 continuations are unchanged.

## Board funding requests and format 32

`data/development-presidents.ts` defines one fictional president per club (generosity 1-5, owner capital per season). `world/board-funding-policy.ts` holds the shared pure rules: `quoteBoardFunding(state, type, clubId, mode)` derives eligibility from the facility quote (money must be the only obstacle), the unclamped `getSpendablePosition` (never while commitments exceed cash) and the refusal cooldown, then decides from `boardConfidenceNow` (the latest review visible at the ledger and date boundary), `requiredBoardConfidence` and `boardCapitalGranted`. `boardFundingRefusal` rebuilds a refusal's wording from recorded evidence for the quote, the Board history and the notice.

Decisions are facilities journal events of type `funding` carrying the amount, mode, approval and evidence (confidence, required confidence, capital remaining). `applyFacilityEvent` recomputes the quote and rejects any difference. An approval books a `board-capital` ledger entry (`boardCapital: { projectId, facilityType }`) through `recordBoardCapital`; the next event must be that upgrade's `start` on the same date at the next ledger index, which pays the full cost. `requestBoardFunding` serves the manager; `automateFacilities` asks only for approved quotes. `facilities.fundingSince` is the opt-in anchor (`enableBoardFunding`; new careers through `NEW_CAREER_SYSTEMS.boardFunding`) and must follow facilities activation, with board reviews enabled.

`validateFacilitiesHistory` exposes `fundingSince` to the replay only from its anchor, requires each approval's immediate start and replays every decision; `validateFinance` accepts the `board-capital` kind from format 32 and requires exactly one entry per approved decision, keyed to the funded project. Formats 1-31 validate as written and migrate with `fundingSince: null`; genuine format-31 continuations are unchanged. In the interface, `ui/focus-when-ready.ts` moves focus after an action only once the autosave has released the inert main region.

## Board season verdicts and format 33

`world/board-consequences.ts` derives a club's verdict from the confidence in its season's final (matchday-ten) review (`seasonVerdict`; thresholds shared with `boardConfidenceLabel`). `board.consequencesSince` is the opt-in anchor (`enableBoardConsequences`; new careers through `NEW_CAREER_SYSTEMS.boardConsequences`). A season is governed only when it is later than the anchor's season; `governingVerdict` then returns the previous season's verdict, and `staffAllocation` / `ownerCapital` scale `STAFF_BUDGET` and the president's capital. Because a season's budget depends only on earlier records, replays need no prefix trimming. `STAFF_BUDGET` is now the base: staff policies, AI coach hiring and renewals, finance appointment guards, board funding quotes and the interface all use the per-season functions.

Staff and finance checks in `season-storage.ts` run before the board is validated, so they read it through a defensive `budgetBoard` helper (a malformed board falls back to standard budgets); `validateBoard` later requires the format-33 anchor to be a real boundary no earlier than board activation and every review to be exact. Formats 30-32 migrate with `consequencesSince: null`; format-32 saves keep `facilities.fundingSince`.

## Press answers, the Inbox and format 34

`world/press-policy.ts` derives the managed club's open press question (`getPressQuestion`) from committed results, current registrations and the relationship journal, so it needs no stored question. Answers are relationship events of type `press` (`answerPress` in `world/relationships.ts`) recording the topic, trigger matchday, answer, addressed squad and regulars; `applyRelationshipEvent` recomputes the question at the event's boundary. `pressImpact` adds a faded, capped contribution to `getPlayerRelationship` morale, so the frozen `prepare` values that feed the match engine include it from the next matchday, and `relationships-validation.ts` replays it like any other relationship command (accepted from format 34). `ui/inbox-items.ts` builds the Inbox from existing records only; `ui/InboxWorkspace.tsx` renders it with the press conference card.

## Rivalries and format 35

`data/development-rivalries.ts` defines the fictional pairs; `world/rivalries.ts` exposes `governingDerby(rivalries, home, away, season, round)`, which returns a rivalry only for matchdays at or after the anchor's `effectiveFrom`. `forecastGate` multiplies derby demand (its `FinanceContext` carries `seasonNumber` and `rivalries`, and ticket validation passes both); `buildBoardReview` adds `rivalryImpact` only to reviews the rivalries govern; `getPlayerRelationship` weights derby results in its recent-results contribution. Because every effect is keyed to `effectiveFrom`, replays at earlier boundaries reproduce the stored gates, reviews and frozen morale without trimming. `SeasonState.rivalries` is validated by `storage/rivalries-validation.ts` (a real boundary, and `effectiveFrom` either a new career's opening or the matchday after activation). Formats 1-34 migrate with rivalries off.

## Facility condition, upkeep plans and format 36

`facilities.maintenanceSince` opts a career in (`enableFacilityMaintenance`; new careers through `NEW_CAREER_SYSTEMS.facilityMaintenance`); upkeep choices are `maintenance` facilities events (`setMaintenancePlan`, and `automateFacilities` for delegated clubs). In `facilities-policy.ts`, `maintenancePlanOn(facilities, club, matchdayDate)` is the latest choice dated before that matchday, and `getFacilityCondition` walks the senior matchday dates after the latest completion and after activation, applying -5 or +10 per matchday. `facilityPracticeBonusPercent`, `getArenaFullCapacity` and `getFacilityUpkeepBreakdown` read condition and plan, so training, gate and upkeep validation rebuild them from the stored history without trimming. Plans and conditions are cached per immutable events array, and matchday date ranges are memoised. The facilities replay exposes `maintenanceSince` from its anchor, like `fundingSince`. Formats 1-35 migrate with `maintenanceSince: null`.

## Club changes and formats 37-38

`SeasonState.career` (`src/domain/career.ts`) holds the opt-in anchor (`enabledSince`; new careers through `NEW_CAREER_SYSTEMS.careerMoves`, older careers through `enableCareerMoves`, effective from the next season) and the chronological `moves` (season, final-matchday date, former and new club, reason, ledger position). `advanceSeason(state, { moveTo })` applies a move on the final matchday after the final board review and before the offseason opens (`appointManager` in `src/world/career.ts`). Replays attribute each decision with `managedClubFor(state, season, offseason)`, or `managedClubAtLedger` for ledger-anchored journals (facilities, sponsorship); `matchClubFor`, used by `managedSide`, keeps the season's final match with the former club through the offseason. A move journals facility control changes as ordinary `delegate` events; the sponsorship replay resets control at a `move` boundary and accepts the former club's best open offer at the move's ledger position, as `automateSponsorship` does; the academy replay releases the former club's prospects (`releaseAcademyFocus`) before the next opening. Formats 1-36 migrate with `createCareer()` (no anchor, no moves).

Format 38 adds the decisions. `seasonEndOutlook` in `src/world/career-policy.ts` rebuilds a season end from stored data only: the final review's verdict for the club managed that season, the final table, vacancies (clubs Under pressure, or the least confident board after a dismissal), `managerReputation` and the resulting offers. `previewSeasonEnd(state)` computes it before the final matchday is committed, for the choice screen; `advanceSeason` rejects a move to a club that made no offer and, without a decision, moves a dismissed manager to the first (best) offer. `validateCareerDecisions` runs after `validateBoard` and requires every governed season end to match: a dismissal needs a `dismissed` move to an offering club, any other move must be `moved` to an offering club. Format-37 saves migrate through `deferCareerDecisions`, which moves `effectiveFrom` to the next season end still to come.

The interface asks before committing: `App.processSeason` sends a `preview` job to `season.worker.ts` on a governed final matchday, shows `SeasonEndChoice` when the outlook has a dismissal or offers, and then sends the `round` job with the chosen `decision` (none to stay). After a move the active match still belongs to the former club, so the sidebar, top bar and Squad page take the managed team from `season.clubs`; `BoardPanel` (`CareerSection`), `ManagerDesk`, `inbox-items.ts` and the competition page read past seasons through `managedClubFor`.


## Senior season summaries and format 45

At rollover, `summarizeSeniorHistory` retains full senior box scores for games involving the club managed **during that season**. Other completed-season games keep their scores, identities, original registration references, injuries and per-player playing time, fouls and participation. `SeasonArchive.summary` stores exact combined player/club totals only for those summarized fixtures; full retained games are added separately by performance selectors. Current-season games remain full. Existing partial/unknown legacy archives stay unknown, without invented statistics. Old formats validate their original complete evidence before migration changes representation.

`senior-history-validation.ts` checks exact roster membership, legal minutes/fouls, nonappearance, canonical summary rows, per-player appearance/minute/foul reconciliation, scoring/shooting identities, team scores/assists and combined steals/blocks. These are explicit summary invariants, not a claim that discarded per-game counting statistics can be reconstructed or authenticated by a portable hash. Historical manager game logs and MVPs remain available; a summarized rival game has no invented box score, rating or MVP. Performance pages distinguish retained totals from detailed match logs. Scouting, morale and press use the retained actual minutes/fouls where their rules need historical evidence.

## Bounded reuse during strict replay

`storage/replay-cache.ts` caches pure academy-week and board objective/review calculations in the codec worker/module. Every strict check still validates raw records, timing, membership, financial anchors and equality against the computed result. Calculation inputs have explicit typed boundaries (`AcademyWeekCalculation`, `BoardCalculationContext`); previously checked academy reports are not input to a later week's point calculation. Reconstructed points advance from calculated outputs, not imported claims.

Keys use exact structural interning of field order, values and array membership, not a probabilistic digest or imported fingerprint. A fresh synchronous scope walks every input anew; object identity is shared only inside that scope while inputs are unchanged. Results use the existing compact JSON codec privately and each hit returns a separate object; outputs JSON cannot preserve exactly are recomputed. Shared field shapes and fixed blocks avoid duplicating long input-prefix keys. Failed validation inside the replay scope clears the cache. The conservative payload/entry budget is 64 MiB and 250,000 entries; overflow clears it and uses ordinary calculations for the rest of that check. Later checks with the same or larger club-season workload bypass cache construction; a smaller workload, explicit reset or new worker may try again. This is only an admission heuristic and never suppresses validation. Legacy-format evidence validates without populating the cache, so its larger representation cannot disable reuse for the migrated current format. These are cache budgets, not measured total JavaScript heap limits. Nothing is persisted in a career or exported file. Cold checks and eviction remain correct, and changed dependencies cause recomputation. Same-state writes and subsequent matchdays can reuse unchanged historical calculations, while all comparison/chronology guards continue to run.
